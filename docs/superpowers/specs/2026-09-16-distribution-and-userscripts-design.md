# Design: Distribution channels and `chrome.userScripts` injection

Status: approved 2026-09-16 (plan written for later execution). Repos: `whatsapp-web-extension` (primary), `whatsapp-backend` (optional managed channel).

## Context

Target users run unmanaged Chrome on Windows. Chrome blocks off-store extension installs there, and
policy-based self-hosting only applies to managed machines. The only broad channel is the Chrome Web
Store. Web Store review enforces the MV3 ban on remotely hosted code; the current page-script
delivery (server-fetched code run through a `blob:` bootstrap injected with `chrome.scripting`) is
exactly that. Chrome's documented exception is the `chrome.userScripts` API, which exists to run
user-supplied or remotely sourced scripts and is exempt from the page CSP in its own right.

Goals:

1. Keep server-delivered page scripts (the property verified on 2026-09-15) while becoming Web Store
   compliant, by injecting through `chrome.userScripts`.
2. Give the extension a stable ID across unpacked, store, and self-hosted builds.
3. Produce the store upload artifact reproducibly.
4. Optionally keep a self-hosted channel (CRX + update manifest served by `whatsapp-backend`) for
   managed or hosted browsers, where policy installs the extension and managed storage supplies credentials.

## Facts the design relies on (Chrome docs, checked 2026-09-16)

- `userScripts` requires the `"userScripts"` permission and host permissions for the target site.
- Availability is gated per extension: Chrome 120–137 by the Developer Mode toggle, Chrome 138+ by the
  "Allow User Scripts" toggle on the extension's details page. Detect availability by calling
  `chrome.userScripts.getScripts()` in a try/catch (it throws when the API is unavailable).
- Scripts may be given as code strings; worlds `USER_SCRIPT` and `MAIN` are supported; `execute()`
  (inject into a specific tab now) needs Chrome 135+.
- Registered scripts persist across browser sessions but not across extension updates: re-register
  in `runtime.onInstalled`.
- Web Store MV3 policy: remotely fetched code may run only via the User Scripts API (or the debugger
  API); the exemption applies solely to code executed through that API.

## Decisions

- **Primary injection = `userScripts`.** Register one persistent script `wabridge-page`
  (`matches: ['https://web.whatsapp.com/*']`, `world: 'MAIN'`, `runAt: 'document_idle'`,
  `js: [{ code }]`). Chrome then injects it on every WhatsApp tab load without the worker. When a new
  page-script version arrives, `userScripts.update` replaces the code, and for tabs already open
  `userScripts.execute` runs the new version immediately (the page script's build stamp already retires
  the older instance).
- **Fallback = current `chrome.scripting` blob bootstrap**, compiled in only for non-store channels.
  Store builds contain no fallback code path at all, so review sees only the exempt API.
- **Build channels** selected by `npm run build -- --channel=<dev|store|managed>`:
  - `dev` (default): unpacked development; fallback on; output `dist/` as today.
  - `store`: fallback compiled out; output `release/store/` (manifest + assets + bundles) and a zip.
  - `managed`: fallback on; manifest gains `update_url`; output `release/managed/` and a signed CRX.
  Channel-specific manifest fields are generated by the build from `manifest.json` (the source of
  truth) plus per-channel overrides; the committed `manifest.json` stays the dev manifest.
- **Fixed extension ID**: `manifest.json` gains a `key` field (public key, committed). The matching
  private key lives outside the repo (`~/.config/whatsapp-web-extension/extension.pem`) and signs the
  CRX; the Web Store honours the `key` on first upload, so all channels share one ID.
- **Popup guidance**: status gains `injection: 'userScripts' | 'bootstrap' | 'none'`. When
  `userScripts` is unavailable, the popup shows how to enable "Allow User Scripts" with a link to
  `chrome://extensions/?id=<id>`. In `store` builds, without the toggle nothing is injected and the
  popup says so plainly.
- **Managed channel is optional** and only for customers with managed devices or hosted browsers:
  the backend serves `GET /extension/update.xml` and `GET /extension/whatsapp-bridge.crx`
  unauthenticated (Chrome fetches them without credentials) from committed resources verified by
  hash at startup, mirroring the page-script catalog.

## Extension changes

- `manifest.json`: add `"userScripts"` permission and `"key"`; add `icons` (16/48/128) which the store requires.
- `background/injector.js` (pure, testable with a fake `chrome` facade):
  - `detect(api) → 'userScripts' | 'bootstrap' | 'none'` (`getScripts()` probe; bootstrap only if compiled in).
  - `ensureRegistered(api, { code, version })`: `getScripts({ids})` → `register` or `update` when the
    stored version differs (version kept in the script `id` suffix or in storage).
  - `executeNow(api, tabId, code)`: `userScripts.execute` when available, else bootstrap, else no-op.
  - `unregister(api)` for cleanup on disconnect if desired (not required).
- `background/index.js`: on hello (new version) → `ensureRegistered` then `executeNow` for the
  attached tab; on tab attach → `executeNow` only if the tab has not reported `injected`/`ready`
  (registered scripts already run on load); `runtime.onInstalled` → re-register from the cached page
  script; status carries `injection`.
- The bootstrap (`bootstrapPageScript`) moves into `background/bootstrap.js`, imported only when
  `__WABRIDGE_CHANNEL__ !== 'store'` (esbuild `define` + dead-code elimination; verify by grepping the
  store bundle for `createObjectURL`).
- The page script itself is unchanged. Its `injected` signal is emitted by the bootstrap today; under
  `userScripts` the worker treats the page's `ready` event as the readiness signal (already supported).
- Popup: `Injection: user scripts` / `Injection: bootstrap (dev)` / `Injection: unavailable — enable
  "Allow User Scripts"` with the link.

## Packaging

- `npm run pack -- --channel=store`: builds the store channel, writes
  `release/whatsapp-web-extension-<version>.zip` containing `manifest.json`, `popup.html`,
  `managed-schema.json`, `icons/`, `dist/*.js`. Version comes from `package.json`.
- `npm run pack -- --channel=managed`: builds, then signs `release/whatsapp-bridge-<version>.crx`
  with the private key and writes `release/update.xml` (Omaha format: appid = extension ID, version,
  codebase URL, SHA-256). Optionally copies both into
  `whatsapp-backend/src/main/resources/wabridge/extension/` (`--sync`).
- Store listing inputs (manual, tracked in the plan): 128×128 icon, at least one 1280×800
  screenshot, short and long description, privacy policy URL, single-purpose statement, permission
  justifications (host permission for web.whatsapp.com, `userScripts` "page script delivered by the
  user's own configured server", `storage`, `alarms`, `unlimitedStorage`, `scripting` for the relay
  re-injection), and the remote-code justification pointing at the User Scripts API.

## Backend (optional managed channel)

- Resources `wabridge/extension/whatsapp-bridge.crx`, `wabridge/extension/update.xml`,
  `wabridge/extension/manifest.json` (`{ "crx": { "version", "sha256", "size" } }`).
- `ExtensionCatalog` validates the hash at startup like `ScriptCatalog`.
- `ExtensionController`: `GET /extension/update.xml` (`application/xml`), `GET /extension/whatsapp-bridge.crx`
  (`application/x-chrome-extension`), both permitted without a token in `SecurityConfig`.
- Deployment note: HTTPS is required for policy-installed update URLs in practice.

## Testing

- Unit: `injector.test.js` with a fake API (available / unavailable / execute missing; register vs
  update by version; store channel never touches `scripting`), build test that the store bundle
  contains no `createObjectURL`/`executeScript` strings, packaging test that the zip contains exactly
  the allowed files and the manifest has no `update_url`.
- Manual: (1) toggle off → popup shows the enable hint, no injection; toggle on → page script runs on
  tab reload without the worker injecting; (2) new page-script version → open tab updates within the
  reconnect window; (3) dev channel with toggle off → bootstrap fallback still works; (4) store zip
  loads via "Load unpacked" from `release/store/` and behaves like (1); (5) optional: managed VM
  installs via `ExtensionInstallForcelist` from the backend URL.

## Out of scope

- Publishing to the store (account, fee, review) — a manual step with a checklist in the plan.
- Delivering worker/relay/popup code remotely (still impossible under MV3).
